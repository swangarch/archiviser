# Layout Architectural Boards

Design the presentation from approved source assets. Do not recreate drawings or renders inside the board.

## Audit assets before layout

Inventory every supplied file: identifier, type, dimensions, orientation, crop tolerance, required scale, caption, status, and geometry/design revision. Read [references/asset-manifest.md](references/asset-manifest.md).

Flag missing, duplicated, low-resolution, contradictory, or obsolete assets. If a required drawing is absent, request or create it through the relevant production skill as a separate file before layout. Use a clearly marked placeholder only when the user approves one.

## Define the board set

Confirm or infer:

- board count, physical size, orientation, bleed, safe margin, and output format;
- viewing distance and minimum readable type/drawing scale;
- required content and jury/client priorities;
- one narrative role for each board;
- shared grid, margins, gutters, typography, numbering, caption, color, and background system.

Generate each board as a separate large-format file. A side-by-side overview is optional and never replaces the individual boards.

## Build a clear narrative

Use a sequence such as:

1. concept, question, site, and strategy;
2. spatial organization, plans, sections, and experience;
3. structure, material, environment, detail, and atmosphere.

Adapt the sequence to the project. Give each board one dominant claim and one dominant visual. Use scale contrast, alignment, grouping, and white space to guide reading; do not give every asset equal weight.

## Place, do not regenerate

- Place the original approved asset or a non-destructive crop of it.
- Preserve its geometry, linework, color, labels, and aspect ratio.
- Never ask image generation to redraw many tiny plans and renders inside a board.
- Do not stretch, mirror, recolor, relight, or repaint content to make it fit.
- Keep standalone originals and record which revision each placement uses.
- Update a board by replacing the linked asset, not by painting over the board image.

## Write concept text responsibly

Extract claims from the project evidence. Organize a concise title, one short concept statement, strategy headings, captions, and optional technical notes. Do not invent performance claims, dimensions, materials, program, or context facts. Use final supplied copy verbatim when provided; otherwise mark draft copy for review.

Read [references/board-system.md](references/board-system.md) for grid and hierarchy rules and [references/delivery-checklist.md](references/delivery-checklist.md) before export.

## Avoid template aesthetics

Avoid crowded mosaics, equal-sized boxes, arbitrary diagonals, oversized decorative titles, weak margins, excessive rules, scattered captions, unrelated palettes, tiny unreadable plans, repeated hero images, generic lorem ipsum, fake logos, and ornamental diagrams. Do not let layout conceal missing design evidence.

## Deliver the board set

Export every board separately at the requested physical size and resolution, plus an optional low-resolution overview or PDF. Report asset revisions, substitutions, placeholders, draft text, and print assumptions. Verify margins, bleed, image resolution, text overflow, line visibility, consistent numbering, cross-board alignment, and reading order.
